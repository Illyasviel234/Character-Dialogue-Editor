# 角色台词剪辑器：完整开发流程与团队分工

## 1. 文档目的

本文定义角色台词剪辑器从需求提出、设计、开发、测试、发布到维护的完整工程流程，并明确各阶段的任务、负责人、协作关系、交付物和质量门禁。

适用范围：

- Windows 桌面 GUI
- Python 命令行工具
- Whisper 日语转写
- ECAPA-TDNN 声纹提取与角色筛选
- FFmpeg 视频剪辑、转码和拼接
- 本地模型、缓存、任务目录和报告生成
- 安装包或完整离线包的发布与维护

本文以一个 5 至 7 人的完整小团队为基准。实际只有 2 至 3 人时，可以一人兼任多个角色，但需求确认、代码评审和发布验收仍应尽量由不同的人完成。

## 2. 项目目标与边界

### 2.1 产品目标

用户输入一段包含日语对白的视频，通过少量目标角色种子台词建立声纹模板，筛选并人工核对目标角色台词，最后生成剪辑成片和核对报告。

核心体验目标：

- 全程本地运行，不上传视频、音频或转写内容
- 同一台设备上可重复处理多个视频，任务数据互不污染
- 用户可以理解候选台词、分数和不确定项
- 导出结果保持音画同步、画面比例和合理的媒体规格
- 中断、失败和重新分析不会破坏上一次有效结果
- 无独立 Python 环境经验的 Windows 用户也能启动和使用

### 2.2 当前产品边界

- 主要支持日语动画对白
- 角色识别依赖已知目标角色种子，属于闭集声纹检索
- 同一声优饰演多个角色时不能只靠声纹完全区分
- 强 BGM、重叠说话和极短台词需要人工复核
- 当前主要面向单机、单用户和本地文件
- 不负责版权授权、内容分发或商业使用许可

### 2.3 非功能目标

| 类别 | 目标 |
|---|---|
| 正确性 | 不跨视频复用错误缓存；成片时间轴误差受控 |
| 可恢复性 | 失败运行不替换上一次完整运行 |
| 性能 | 25 分钟素材在目标 GPU 上约数分钟完成分析 |
| 隐私 | 默认不联网、不上传素材、不写入外部服务 |
| 兼容性 | Windows 10/11，CPU 可运行，CUDA 可加速 |
| 可维护性 | GUI 与 CLI 共用核心逻辑，关键纯函数有自动测试 |
| 可观测性 | 日志明确显示阶段、运行 ID、错误和输出位置 |

## 3. 团队角色与职责

### 3.1 标准团队配置

| 角色 | 建议人数 | 核心职责 |
|---|---:|---|
| 产品负责人 PM | 1 | 用户场景、需求优先级、验收标准、版本范围 |
| 技术负责人 TL | 1 | 架构、技术决策、代码评审、质量与发布把关 |
| 桌面端工程师 | 1 | PySide6 GUI、交互、状态管理、可用性与无障碍 |
| 算法工程师 | 1 | 转写、声纹、阈值、评估数据与算法指标 |
| 媒体工程师 | 1 | FFmpeg、音视频时间轴、编码、格式兼容和性能 |
| 测试工程师 QA | 1 | 测试策略、自动化、兼容性、回归和发布验收 |
| 发布与运维工程师 | 0.5 至 1 | 依赖、构建、签名、发布包、升级与问题收集 |

### 3.2 小团队兼任方案

三人团队建议：

| 人员 | 兼任职责 |

| B | TL、桌面端、核心数据层、发布 |
| C | 算法、媒体处理、自动化测试 |

两人团队建议：

| 人员 | 兼任职责 |

## 4. 项目管理方式

### 4.1 迭代节奏

建议使用两周一个迭代：

1. 第 1 天：需求梳理、风险识别、任务拆分和估算。
2. 第 2 至 7 天：设计、开发、单元测试和持续评审。
3. 第 8 至 9 天：集成、媒体兼容性和回归测试。
4. 第 10 天：版本验收、发布候选构建和迭代复盘。

紧急 Bug 使用独立修复分支和缩短流程，但不能跳过复现用例、代码评审、回归测试和发布记录。

### 4.2 工作项结构

每个需求或 Bug 至少包含：

- 背景和用户问题
- 明确范围与不处理范围
- 可验证的验收标准
- 设计或技术方案链接
- 风险与回退方案
- 负责人和评审人
- 测试范围
- 文档更新项

Bug 还应包含：

- 复现环境
- 最小复现步骤
- 预期结果和实际结果
- 日志、输入元数据和输出元数据
- 严重程度和影响范围
- 根因，而不只是表面修复

### 4.3 优先级定义

| 等级 | 定义 | 处理要求 |
|---|---|---|
| P0 | 数据错配、错误成片、破坏已有结果、严重隐私或安全问题 | 停止发布，立即修复 |
| P1 | 主流程失败、结果明显不可靠、无合理绕行方式 | 当前迭代修复 |
| P2 | 次要功能异常、性能或体验问题，有可接受绕行方式 | 排入近期版本 |
| P3 | 优化建议、轻微文案或低频边界 | 进入待办并定期整理 |

## 5. 完整开发流程

## 阶段 0：立项与可行性验证

### 目标

确认用户问题真实存在，并验证本地转写、声纹筛选和视频导出在目标硬件上可行。

### 主要任务

- 收集目标用户、素材类型、典型时长和输出需求
- 明确支持语言、操作系统、GPU 和离线要求
- 选取有合法使用权限的验证素材
- 快速验证 Whisper、ECAPA 和 FFmpeg
- 估算模型体积、运行时间、内存和显存
- 识别同声优、多角色、BGM、重叠语音等算法限制
- 制定成功指标和终止条件

### 人员分工

- PM：用户访谈、场景、价值和范围
- TL：技术可行性和架构风险
- 算法：建立最小转写与声纹实验
- 媒体：验证抽音频、切片和拼接
- QA：定义可测性和基础样本矩阵

### 交付物

- 项目立项说明
- 可行性实验记录
- 初始风险清单
- 初始性能基线
- MVP 范围与成功指标

### 退出条件

- 至少一个真实样本跑通端到端流程
- 识别准确率和处理时间达到可接受下限
- 已知限制被产品负责人接受
- 数据隐私和素材使用方式明确

## 阶段 1：需求分析

### 目标

将概念转化为可实现、可测试、可验收的需求。

### 主要任务

- 绘制用户主流程和异常流程
- 定义输入格式、音轨选择和输出规格
- 定义分析、复核、导出和报告功能
- 定义任务缓存、中断恢复和重新分析行为
- 定义错误信息、进度和日志要求
- 区分 MVP、后续版本和明确不做的功能
- 为每个功能编写验收标准

### 重点用户流程

1. 首次启动和环境检查。
2. 选择视频并读取媒体信息。
3. 启动分析并观察进度。
4. 分析失败、取消和重新运行。
5. 用关键词或手工种子计算相似度。
6. 试听、筛选和人工修正。
7. 调整合并间隔、留白和输出规格。
8. 生成成片和报告。
9. 重新打开历史任务。

### 人员分工

- PM：编写需求和验收标准，对优先级负责
- 桌面端：评估交互可行性和状态数量
- 算法：定义分数含义、种子要求和限制
- 媒体：定义支持格式和输出约束
- QA：补充边界、异常和兼容性需求
- TL：确认范围与技术成本匹配

### 交付物

- 产品需求文档
- 用户流程图
- 验收标准清单
- 输入输出格式说明
- 风险与依赖清单

### 退出条件

- 所有 P0/P1 需求都有明确验收标准
- 不存在“结果正确”“体验良好”等不可验证描述
- 产品、研发和测试对范围达成一致

## 阶段 2：技术设计

### 目标

在编码前确定模块边界、数据格式、状态机、失败恢复和测试方法。

### 主要任务

- 划分 GUI、核心层、算法脚本、媒体层和持久化层
- 设计 source ID、内容指纹、job、run 和 manifest
- 设计 `running -> transcribed -> complete/failed` 状态机
- 定义 transcript、embeddings、selected 和报告格式版本
- 设计 FFmpeg filter graph 和音视频时间轴规则
- 设计进程调度、取消、超时和临时文件
- 设计依赖管理、离线模型发现和发布包结构
- 编写关键技术决策记录 ADR

### 架构原则

- GUI 与 CLI 调用同一核心逻辑
- 任务身份基于内容，路径只作为元数据
- 未完整提交的运行不可成为活动结果
- 用户输出使用临时文件完成后再替换
- 报告只读取结构化任务数据，不使用作品硬编码
- 媒体规格由 ffprobe 探测，不凭样本假设
- 算法变更必须有标注集指标

### 人员分工

- TL：架构和数据契约最终负责
- 桌面端：GUI 状态和进程接口设计
- 算法：模型输入输出及评估方案
- 媒体：时间轴、流映射和编码方案
- QA：可测试性、故障注入和测试夹具
- 发布：依赖、模型和构建约束

### 交付物

- 技术设计文档
- 数据结构和状态机说明
- ADR 记录
- 测试策略初稿
- 性能与兼容性预算
- 迁移与回退方案

### 退出条件

- 关键状态和失败路径均有处理方案
- 数据格式可被独立验证
- 高风险设计已完成技术评审
- 测试工程师确认方案可自动化验证

## 阶段 3：迭代计划与任务拆分

### 目标

将设计拆成可独立开发、评审和验证的小任务。

### 拆分原则

- 单个任务尽量在 0.5 至 2 天内完成
- 每个任务对应明确交付物和测试
- 数据格式改动与消费者改动在同一迭代完成
- 高风险底层工作早于 UI 包装
- 性能优化与正确性修复分开评审

### 示例任务包

| 任务包 | 负责人 | 评审人 | 交付物 |
|---|---|---|---|
| 内容指纹与任务目录 | TL | QA | manifest 模块和单测 |
| run 状态机 | TL | 桌面端 | 状态转换、故障测试 |
| 转写任务接入 | 算法 | TL | 转写产物与错误处理 |
| 声纹与评分 | 算法 | QA | embeddings、评分和指标 |
| 单次剪辑 filter graph | 媒体 | TL | 导出实现和时长测试 |
| GUI 分析状态 | 桌面端 | QA | 进度、取消、重试 |
| 报告与文件名 | 桌面端 | PM | HTML/CSV 和命名规则 |
| 离线发布包 | 发布 | TL | 构建脚本和验证记录 |

### 退出条件

- 每项任务有负责人、评审人、验收标准和估算
- 依赖关系清晰
- 本迭代容量不超过团队实际能力

## 阶段 4：开发实现

### 开发步骤

1. 从最新稳定分支建立短生命周期功能分支。
2. 先添加失败测试或最小复现。
3. 实现最小范围改动。
4. 执行相关单元和集成测试。
5. 更新说明、数据版本和变更记录。
6. 提交代码评审。
7. 根据评审意见修改并重新测试。

### 编码要求

- 路径统一从 `work/core/paths.py` 获取
- 用户文件名统一经过 `safe_filename()`
- JSON 使用原子写入
- 子进程参数使用列表，不拼接 shell 字符串
- 结构化数据使用 JSON/NPZ API
- 失败应返回非零退出码并输出具体阶段
- 临时文件、缓存和用户正式输出分开
- 模块导入不应产生不可预期写操作
- 模型和大型资源仅在需要时加载

### 代码评审清单

- 是否满足验收标准
- 是否破坏已有任务格式
- 是否存在跨视频或跨 run 数据混用
- 失败和取消是否保留上次有效结果
- 临时文件是否清理
- Windows 路径和 Unicode 是否正确
- FFmpeg 流映射和时间轴是否正确
- 新逻辑是否有必要的测试
- 文档是否与实现一致

### 人员分工

- 开发负责人：实现、自测和说明
- 指定评审人：代码、风险和测试评审
- QA：提前准备验收数据，不等待开发结束
- TL：评审跨模块和高风险改动

### 退出条件

- 代码评审通过
- 新旧自动测试通过
- 无未解释的警告和临时调试代码
- 文档和版本字段已同步

## 阶段 5：持续集成与静态质量检查

### 必须执行的检查

```powershell
.venv\Scripts\python.exe -m compileall -q gui work tests
.venv\Scripts\python.exe -m unittest discover -s tests -t . -v
```

条件允许时增加：

- Ruff 或 Flake8 静态检查
- 类型检查
- 依赖漏洞扫描
- 文档链接检查
- 打包后导入和启动检查

### 质量门禁

- 编译失败：禁止合并
- 单元或集成测试失败：禁止合并
- P0/P1 已知回归：禁止发布
- 数据格式变更无迁移方案：禁止发布
- 媒体时间轴超出允许偏差：禁止发布

### 人员分工

- TL：定义门禁并处理例外
- QA：维护测试集和失败归因
- 发布：维护构建环境
- 开发人员：修复本人改动引发的失败

## 阶段 6：测试与验证

### 6.1 单元测试

负责人：开发人员编写，QA 评审覆盖。

范围：

- 内容指纹和 source ID
- manifest 状态转换
- 混合产物、缺失产物和错误维度拒绝
- 声纹模板和阈值统计
- 片段合并、留白和边界
- 文件名净化
- 媒体探测辅助函数

### 6.2 集成测试

负责人：QA，媒体和算法工程师协助。

范围：

- FFmpeg 合成短素材后的真实导出
- 单段、双段和多段时长
- 音视频结束时间差
- 23.976、25、30 fps 和可变帧率
- 横屏、竖屏和非 16:9
- 有音轨、无音轨和多音轨
- CPU 回退和 CUDA 路径
- 中断转写和中断导出
- 失败后活动 run 保持不变

### 6.3 算法评估

负责人：算法工程师，PM 和 QA 共同确认标注。

每个标注样本记录：

- 真实角色标签
- 台词 ID 和时间范围
- 是否有 BGM、重叠说话、音效或极短语音
- 模型、种子和分数
- 人工复核结论

至少报告：

- Precision
- Recall
- F1
- 不同阈值命中数量
- 按干扰类型拆分的指标
- 与上个稳定版本的差异

### 6.4 GUI 测试

负责人：QA 与桌面端工程师。

覆盖：

- 首次启动和缺少资源
- 视频切换和旧状态清空
- 关键词无命中
- 手工种子与重新评分
- 运行时控件禁用
- 取消、关闭窗口和重新启动
- 高 DPI、不同窗口尺寸和长路径
- 中文、日文和非法文件名字符

### 6.5 验收测试

负责人：PM 最终验收，QA 提供证据。

验收使用接近真实用户的素材和步骤，不能只使用开发样本。所有结果应记录版本、硬件、耗时、参数和输出媒体信息。

### 测试退出条件

- 所有 P0/P1 用例通过
- 自动测试全部通过
- 核心兼容性矩阵完成
- 算法指标不低于发布基线
- 无未处理的高风险 Bug

## 阶段 7：发布准备

### 主要任务

- 更新版本号和变更日志
- 冻结依赖和模型版本
- 生成可重复构建的发布包
- 验证全新 Windows 环境启动
- 验证无 CUDA 时 CPU 回退
- 检查模型、FFmpeg 和第三方许可证
- 准备升级、回退和数据迁移说明
- 创建发布候选版本 RC

### 发布包检查

- 不包含版权受限的测试素材
- 不包含用户输入、输出或历史任务
- 不包含开发日志和临时文件
- 模型文件完整且可离线加载
- 启动脚本使用相对路径
- 文档、版本与二进制一致
- 校验和已生成

### 人员分工

- 发布工程师：构建、签名、校验和和发布包
- QA：在干净环境执行发布验收
- TL：批准技术发布
- PM：批准产品发布
- 算法和媒体：核对模型与编码版本

### 退出条件

- RC 在干净环境通过完整冒烟测试
- 发布检查表全部签字
- 回退包和回退步骤可用
- 已知问题明确写入发布说明

## 阶段 8：发布

### 发布步骤

1. 为稳定提交创建版本标签。
2. 保存源码、依赖、模型和工具版本清单。
3. 上传发布包与校验和。
4. 发布变更说明、安装说明和已知限制。
5. 执行一次发布后冒烟测试。
6. 记录发布时间、负责人和制品位置。

### 发布后观察

首个工作日重点观察：

- 启动失败
- CUDA/CPU 模型加载失败
- 路径和权限问题
- 缓存迁移或任务无法加载
- 成片时长、音画同步或黑屏
- 杀进程后残留 FFmpeg

## 阶段 9：维护与问题响应

### 问题处理流程

1. 收集版本、系统、硬件和复现步骤。
2. 收集去隐私的日志和 ffprobe 元数据。
3. 确认严重程度和影响范围。
4. 创建最小复现或自动测试。
5. 定位根因并评估是否需要数据迁移。
6. 修复、评审、回归并发布补丁。
7. 将经验补入测试集和文档。

### 数据收集原则

- 默认不收集用户媒体和转写文本
- 日志避免记录完整外部绝对路径
- 用户主动提供样本时明确用途和保存周期
- 问题解决后删除不再需要的素材

### 定期维护

每月：

- 整理 Bug、性能数据和常见失败
- 检查依赖和模型兼容性
- 清理废弃脚本和重复文档

每季度：

- 扩充跨作品算法标注集
- 重跑完整兼容性矩阵
- 评估 Python、PySide6、FFmpeg 和模型升级
- 检查发布包体积和启动性能

## 6. 分支、提交与版本策略

### 6.1 分支策略

建议使用轻量主干开发：

- `main`：始终保持可发布
- `feature/<name>`：功能开发
- `fix/<name>`：一般 Bug 修复
- `hotfix/<name>`：生产级紧急修复

功能分支应短生命周期，合并前同步主干并完成全部门禁。

### 6.2 提交要求

每个提交：

- 只包含一个逻辑主题
- 信息说明“为什么改”和“改了什么”
- 不提交输入视频、输出成片、模型、虚拟环境和任务缓存
- 不混入无关格式化和生成文件

### 6.3 版本规则

建议使用语义化版本：

- 主版本：任务格式或使用方式不兼容
- 次版本：向后兼容的新能力
- 修订版本：兼容的 Bug 修复

模型、manifest 和 selected 等数据格式还需拥有独立格式版本，不能只依赖应用版本。

## 7. Definition of Ready

任务进入开发前必须满足：

- 用户问题和目标明确
- 范围与不处理范围明确
- 验收标准可执行
- 输入、输出和异常情况明确
- 依赖和风险已识别
- 负责人和评审人确定
- 测试方法可行

## 8. Definition of Done

任务完成必须满足：

- 实现符合验收标准
- 代码通过评审
- 自动测试通过
- 新风险有对应测试或监控
- GUI 与 CLI 行为一致
- 文档、帮助文本和示例已更新
- 没有残留调试文件或硬编码样本数据
- 对用户数据格式的影响已说明
- 发布或回退步骤明确

## 9. 项目专用质量指标

## 11. 推荐版本路线
