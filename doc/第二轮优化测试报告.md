## 5. 新发现问题与 Debug 建议

### P0：部分哈希会发生可复现的任务 ID 碰撞

相关代码：`work/core/manifest.py:32`。

#### 现象

当前指纹只读取：

- 文件大小
- 文件头 1 MiB
- 文件尾 1 MiB

定向测试创建了两个 3 MiB、同名、同大小的文件：头部和尾部相同，中间 1 MiB 完全不同。结果：

```text
fingerprint A = 998b1334ce4c581c
fingerprint B = 998b1334ce4c581c
source ID 相同
```

这与代码和 README 中“不同内容必不同 ID”的承诺不一致。

#### 影响

同一路径中的视频若只修改中部且保持大小，或者两个媒体文件恰好拥有相同头尾结构，可能复用错误任务缓存。该问题会重新引入跨视频时间码和声纹混用风险。

#### 修复建议

优先方案：首次导入时流式计算完整 SHA-256 或 BLAKE2b，结果写入 manifest。后续可使用路径、大小和高精度修改时间快速命中缓存，只在元数据变化时重新计算完整指纹。

若必须使用快速采样哈希，应至少：

- 分布式读取多个等距块
- 加入纳秒级修改时间
- 文档明确其为概率指纹
- 在正式加载缓存前增加媒体流摘要校验

对于本项目，正确性比首次多读取一次视频更重要，推荐完整文件哈希。

必须新增测试：只修改文件中间内容时，指纹和 source ID 必须变化。

### P1：selected 没有在导出前绑定 active run

相关代码：

- `work/cut.py:110`
- `work/gen_report.py:32`

#### 现象

`selected.json` 已包含 `run_id`，但 `cut.py` 和 `gen_report.py` 没有检查：

```text
selected.run_id == manifest.active_run(source_id)
```

当前样本二者恰好一致，因此测试通过。但重新分析成功后，如果用户没有重新生成选择方案，命令行直接执行 `cut.py` 或 `gen_report.py`，仍会使用旧 run 的台词和时间码。

#### 修复建议

增加公共函数 `validate_selection(sid, selected)`，至少校验：

- source ID 一致
- selected run ID 等于 active run
- source fingerprint 一致
- 所有片段位于源时长内
- 台词 ID 存在于 active transcript

`cut.py`、`gen_report.py` 和 GUI 导出前共同调用。旧选择方案应提示用户重新筛选，不应静默继续。

### P1：run 校验没有验证 embeddings 行数与 ID 数量一致

相关代码：`work/core/manifest.py:180`。

#### 现象

构造以下产物：

- `emb.shape == (2, 192)`
- `ids.shape == (1,)`

`validate_run()` 仍返回成功：

```text
True, "2 段 / 1 条声纹"
```

后续 `zip(ids, scores)` 会静默截断数据，问题不容易被发现。

#### 修复建议

校验以下条件：

- `emb.shape[0] == len(ids)`
- ID 唯一
- ID 类型可转换为整数
- 向量全部为有限数值
- 每行向量范数大于零
- transcript 的 `run_id` 必须严格等于当前 run ID
- transcript 的 `source_id` 必须存在且严格一致

增加行数不一致、重复 ID、NaN、Inf、零向量和错误 run ID 测试。

### P1：允许输出路径覆盖源视频

相关代码：

- `work/cut.py:38`
- `work/cut.py:144`

#### 现象

`--output` 会转换为绝对路径，但没有阻止其与输入视频相同。定向检查确认：把源视频路径传给 `--output` 后，解析结果与输入完全相同。

编码完成后 `os.replace(tmp_out, out_path)` 会覆盖原视频。

#### 修复建议

在启动 FFmpeg 前比较规范化路径：

```python
if os.path.normcase(os.path.abspath(video)) == os.path.normcase(out_path):
    sys.exit("输出路径不能与源视频相同")
```

对于已存在的其他输出文件，建议继续允许 `-y` 覆盖，但 GUI 可给出明确确认。必须增加“输出等于输入时拒绝”的测试。

### P1：新分析会遗留旧的未完成 run

相关代码：

- `work/core/manifest.py:142`
- `work/core/manifest.py:261`

#### 现象

连续调用两次 `new_run()` 后：

- 第二个 run 成为 `pending_run`
- 第一个 run 仍保持 `running`
- `cleanup_runs()` 不删除 `running` 或 `transcribed` 的非 pending run

硬终止进程时无法执行异常处理，长期使用后会积累孤立目录。

#### 修复建议

创建新 run 时，将已有 pending run 标记为 `abandoned`。清理策略应删除：

- 非当前 pending 的 `running/transcribed`
- 超过一定时间的未完成 run
- `failed/abandoned` run

如需支持断点恢复，应把“继续旧 run”和“开始新 run”设为显式操作。

### P2：输出继承源文件章节数据轨

真实源视频包含一个 `bin_data/text` 数据流。虽然命令显式映射了视频和音频，FFmpeg 仍根据源章节元数据在输出中生成数据轨：

```text
stream 0: H.264 video
stream 1: AAC audio
stream 2: bin_data, handler SubtitleHandler
```

#### 影响

- 输出包含与剪辑内容无关的源章节信息
- 可能泄露标题、章节或其他元数据
- 某些播放器可能显示错误章节
- 当前合成素材测试无法发现该问题

#### 修复建议

默认导出增加：

```text
-map_metadata -1 -map_chapters -1
```

需要保留的基础标签由程序重新写入。增加带章节或数据轨的合成测试，并断言输出流类型仅包含预期的视频和音频。

### P2：无效媒体仍返回非空探测结果

对内容为 `not media` 的伪 MP4 调用 `media.probe()`，结果为包含零值字段的字典，而不是空字典。`cli.prepare()` 因此不会报告“无法探测视频”，后续才以“无音轨”等次级错误失败。

建议检查：

- ffprobe 返回码
- 是否存在有效视频流
- duration、width 和 height 是否合理

探测失败时返回空字典或抛出明确异常。

### P2：当前 VFR 与多音轨行为尚未验证

当前导出使用源 `r_frame_rate` 并强制 CFR。对 VFR 素材，这不等同于“保持源规格”。此外，分析和导出都默认使用第一条音轨。

建议：

- 媒体探测同时保存 `avg_frame_rate` 和 VFR 判断
- VFR 素材明确选择转 CFR 或保留时间戳
- GUI 提供音轨选择
- 增加 VFR、25 fps、30 fps、无音轨和多音轨测试
