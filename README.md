# 角色台词剪辑器

按角色声纹自动筛选动画片段，全程本地离线运行。

输入一集动画，输出只包含指定角色台词的剪辑片段。不需要字幕文件，不需要联网，不上传任何素材。

![界面预览](gui/preview.png)

## 工作原理

核心难点是：视频里没有"谁在说话"的信息。所以走的是**闭集声纹检索**，而不是通用的说话人分离。

```
抽音频 → 日语转写（逐句时间轴）→ 逐句提取声纹向量
      → 用几句已确认属于目标角色的台词建立模板
      → 全片相似度打分 → 阈值筛选 + 人工核对 → 精确切割拼接
```

为什么不用 WhisperX + pyannote 那套通用方案：它们解决的是"开放集"问题，输出 `speaker_0 / speaker_1 / speaker_2` 这样的匿名标签，你还得自己听一遍才知道哪个是目标角色。而且 pyannote 训练集是会议和广播语音，动画配音的夸张演技 + BGM + 音效属于明显的域外数据，聚类数量经常不准。

本项目把问题改成"已知目标角色，判断每句是不是她"，绕开聚类这一步。

模板不是简单平均：先算种子与中心的相似度，用中位数和 MAD 剔除离群种子再求均值，混入的误识别或情绪极端的台词不会把模板拉偏。

## 准确率

在人工逐条核对过的 32 句标注集上评估（`work/eval_threshold.py --labels builtin`）：

| 阈值 | 精确率 | 召回率 | F1 | 命中数 |
|---|---|---|---|---|
| 0.62 | 0.788 | 0.812 | 0.800 | 33 |
| 0.64 | 0.926 | 0.781 | 0.847 | 27 |
| **0.66** | **0.962** | **0.781** | **0.862** | 26 |
| 0.68 | 1.000 | 0.750 | 0.857 | 24 |
| 0.70 | 1.000 | 0.562 | 0.720 | 18 |

默认阈值取 **0.66**（F1 最高）。想要零误判可以提到 0.68，代价是漏掉约四分之一台词。

稳健模板与简单平均在同一阈值下的对比：0.66 时 F1 为 0.862 / 0.847，0.62 时差距更大（0.800 / 0.761）。

界面上点「保存人工样本」会把当前勾选与临界未勾选存进 `labels.json`，`eval_threshold.py` 默认优先读它。**注意**：如果这些勾选没有逐条人工核对过，它们本身就是阈值筛出来的结果，在对应阈值上的指标会偏乐观（本例会显示 F1 1.000 @ 0.66）。想看独立评估就用 `--labels builtin`。

负样本抑制（用复核后判为"不是她"的临界句扣分）做了 margin 扫描，在当前标注上最好只有 0.981 @ 0.60，不如默认模板，因此生产逻辑里默认不启用——`scoring.template_scores(neg_ids=...)` 保留了参数，供后续数据集验证。

## 快速开始

### 图形界面

双击根目录的 `启动界面.bat`。

操作四步：

1. **选择视频** —— 默认已载入 `input/` 下的文件，也可以点「选择」换别的。多音轨素材可以在「音轨」里选第几条
2. **点「开始分析」** —— 抽音频 + 日语转写 + 声纹提取，25 分钟片源约 3 分钟
3. **核对勾选** —— 这是最花时间也最需要人的一步：
   - 选中一行，按**空格**试听这一句，右下角同时显示该句起始帧
   - **C** 切换勾选、**L** 循环播放、**Esc** 停止、**回车**重播
   - 「显示」可切到「阈值附近」，只看最容易误判的那一段；「排序」可按相似度或时长排
   - 分数按区间着色：0.6 以上青色，0.4–0.6 黄色，更低灰色
   - 核对完点「保存人工样本」，把这次的判断记进 `labels.json`，供 `eval_threshold.py` 评估
4. **点「生成成片」** —— 按当前勾选切割拼接。输出路径默认是 `output/<源名>_<角色>_clip.mp4`，可以直接改「输出到」输入框，或点「浏览」另存到任意位置；清单会跟成片放在同一目录

界面左下角实时显示「已选 N 句 → M 个片段，成片 X 分 Y 秒」。试听用的是 16 kHz 单声道（分析用的同一份音频）加一张起始帧，不启动完整播放器——这样核对一句话只要零点几秒。

### 批量：任务队列

右侧第二个页签是**任务队列**，适合一次处理多集或多角色：

1. 在左栏设好参数（角色名、特征词、阈值、留白、输出规格），点「加入当前视频」
2. 换视频、换角色，再点一次；队列条目会记住加入时的剪辑参数
3. 设好「队列输出目录」，点「开始队列」

队列按顺序执行，每条会自动判断：**已有分析结果就直接切，没有就先跑分析**。音轨变了也算"没有"，会重新分析。状态列显示「等待 / 进行中 / 完成 / 失败 / 已取消」，输出文件列显示实际写入的文件名，说明列显示复用了哪个运行或失败原因。

几个防止"结果对不上"的设计：

- **源文件身份入队即冻结**：条目记下指纹、大小、修改时间，输出名里的摘要也取自这一刻。同一路径被换成别的文件时，表格立刻标红提示，点「开始队列」会被拦下；确认要用新文件就选中该行点「更新源」
- **输出目录是队列级的**：点「开始队列」时统一应用到所有未完成条目，已完成的不动；表格里的文件名会跟着实时变化，不用猜
- **文件名带源指纹短摘要**：`same_碧翠丝_a59803e8_clip.mp4`。`D:/s1/same.mp4` 和 `E:/s2/same.mp4` 角色相同时不会再算出同一个路径
- **启动前三道检查**：源文件身份 → 输出路径冲突（成片/CSV/HTML 三类）→ 目标文件是否已存在。已存在时不会静默覆盖，弹窗让你选「跳过已存在」或「覆盖」
- **完成状态可复核**：标记完成的条目会检查成片能否播放、CSV/HTML 是否还在，产物丢了就自动退回「等待」重新生成
- **运行中锁定队列结构**：上移、下移、移除、清空、更新源在运行期间禁用；条目带稳定 id，完成结果按 id 回写，不会因为顺序变化记到别的任务上

队列存在 `work/queue.json`，关掉程序再打开还在；上次被强杀时停在「进行中」的条目，下次打开会回到「等待」。

## 任务隔离与数据完整性

每个源视频对应 `work/jobs/<源文件ID>/`，ID 由文件名加**内容指纹**生成。指纹是整个文件的流式 BLAKE2b，不是头尾采样——早期版本只读首尾各 1 MiB，两个头尾相同、中间不同的文件会算成同一个 ID，从而复用错误的转写与时间码。

788 MB 的片源完整哈希约 1 秒，结果按（路径, 大小, 纳秒修改时间）缓存在 `work/.cache/`，切换视频时直接命中，不重复读盘。缓存假设文件内容变化时大小或修改时间至少有一项会变；若外部工具原地改写同尺寸文件并恢复修改时间，用 `migrate_jobs.py --rehash` 重算。

每次分析是一个独立的 run：

```
work/jobs/re0_1_08-a59803e863c31582/
├── manifest.json              源身份 + 运行记录
├── selected.json              切点方案（schema 2：源 ID、run、音轨、指纹、每段时长）
├── labels.json                人工核对结果（点「保存人工样本」后生成）
└── runs/
    └── 20261023-111240-72ee95/
        ├── audio.json           这份 16k 音频来自第几条音轨
        ├── audio16k.wav         分析音频（与转写同生命周期）
        ├── transcript.json
        └── embeddings.npz
```

**音频按 run 隔离**。早期版本把 `audio16k.wav` 放在任务目录，新分析一开始就覆盖它；如果随后转写或声纹失败，旧活动 run 的转写还是旧的、试听却已经是另一条音轨。现在每次抽取只写自己的 run 目录，先写 `.tmp.wav`、探测合法后再原子替换，失败或取消时旧 run 的音频、转写、声纹、试听全部不受影响。

分析分三阶段提交：`running` → `transcribed` → `complete`。声纹阶段结束后校验两份产物是否自洽才标记 `complete` 并设为 `active_run`：

- 转写必须带 `source_id` 与 `run_id`，且与本次运行一致
- 声纹维度 192、行数等于编号数、编号无重复
- 向量全部为有限值、无零向量
- 每条声纹都能在本次转写里找到对应台词
- 运行记录的音轨号与 `audio.json` 一致，且音频文件存在

只有 `complete` 的活动运行会被加载。因此"转写成功但声纹失败"不会把半套转写/声纹设为活动 run。分析音频也在这个 run 目录里，所以未完成的新分析不会改变旧 run 的试听结果。

开始新分析时，之前停在 `running`/`transcribed` 的运行会被标记为 `abandoned`，随后由 `cleanup_runs()` 连同 `failed` 一起回收，进程被强杀也不会留下孤立目录。

### 导出前校验

`cut.py`、`gen_report.py` 和界面导出前都会调用同一个 `validate_selection()`，要求：

- 切点方案 schema 版本为 2（旧方案明确拒绝，不做猜测）
- `source_id` 必填且与源文件一致；源指纹一致
- `run_id` **等于当前活动运行**，否则提示重新生成
- **`audio_track` 等于活动运行所用的音轨**——时间码和声纹来自哪条音轨，导出就必须用哪条
- 每段 `dur` 与 `end - start` 一致（±1 ms）、为有限正数、落在源时长内
- 片段引用的台词编号都存在于当前转写

重新分析后忘了重新筛选时，命令行不会静默用旧时间码切片，而是直接拒绝：

```
切点方案不可用：切点方案来自旧运行 20200101-000000-deadbe（当前 20261023-111240-72ee95），请重新生成切点方案
```

音轨被换过也一样拒绝：

```
切点方案不可用：切点方案用的是第 2 条音轨，当前分析用的是第 1 条，请重新生成切点方案
```

`cut.py --audio-track` 不是"覆盖导出音轨"的开关，而是一致性断言：与分析音轨不符就报错并提示重新分析。界面上切换音轨后会直接禁用「生成成片」，并说明需要重新分析。

旧版扁平缓存（`work/transcript.json`）不再自动迁移，因为旧文件没有来源指纹，无法判断归属。需要手动确认：

```bash
cd work && ../.venv/Scripts/python.exe import_legacy.py --yes
```

指纹算法升级后（v3 → v4），旧任务目录的 ID 会失配；音频布局升级后（任务级 → run 级）也要搬一次。迁移脚本把两件事一起做，确认大小与时长都没变才改名：

```bash
cd work && ../.venv/Scripts/python.exe migrate_jobs.py --dry-run   # 先看会改什么
cd work && ../.venv/Scripts/python.exe migrate_jobs.py
cd work && ../.venv/Scripts/python.exe migrate_jobs.py --rehash    # 忽略指纹缓存重算
```

指纹缓存按（路径, 大小, 纳秒修改时间）命中，这是"切换视频不重读 788 MB"的代价：如果外部程序原地改写同尺寸内容又把修改时间改回去，缓存会返回旧摘要。遇到这种怀疑时用 `--rehash` 或清掉 `work/.cache/fingerprints.json`。

## 可调参数

| 参数 | 默认 | 作用 |
|---|---|---|
| 角色名 | — | 写入报告标题和输出文件名 |
| 台词特征词 | `かしら,ベティ` | 自动挑选种子台词。词越独特越好，`のよ` 这类通用语尾会引入误判 |
| 相似度阈值 | 0.66 | 越高越严格，标注集评估的最优 F1 点 |
| 合并间隔 | 2.0 秒 | 相邻台词间隔小于此值合并为一段 |
| 前 / 后留白 | 0.25 / 0.30 秒 | 每段前后的呼吸空间，会自动避让其他角色的语段 |
| 音轨 | 第 1 条 | 多音轨素材可选；换音轨后必须重新分析，导出校验会拒绝且「生成成片」按钮禁用 |
| 输出 | 保持源规格 | 也可选 1080p / 720p，缩放时保持比例、黑边补齐 |
| 帧率 | 转恒定帧率 | VFR 素材可选「保留源时间戳」 |
| 输出路径 | `output/<源名>_<角色>_clip.mp4` | 界面可编辑或浏览另存；清单与成片同目录；已存在时先确认覆盖 |
| CRF | 20 | 数值越小画质越好、文件越大 |

## 导出规格

默认「保持源规格」：不缩放、不强制帧率，输出宽高、帧率、像素比与源一致（实测 3840×2160 / 23.976 fps / SAR 1:1 完全保持）。只有显式选择 1080p 或 720p 才缩放，且用 `force_original_aspect_ratio=decrease` 加补边，不会拉伸。

切割采用**单次 filter graph 编码**：所有片段作为独立输入 seek 到各自位置，经 `setpts/asetpts` 归零后在 concat filter 里拼接，只做一次 H.264/AAC 编码。这样不会出现"每段分别编码再流复制拼接"时的 AAC 延迟与时间戳舍入累积。

切点会先吸附到帧网格再编码，保证每段是整数帧。实测 14 段 101.99 秒的计划，成片视频流偏差 41 ms（约 1 帧）；视频流 102.060292 秒，音频流 102.083604 秒，结束时间相差约 23 ms。

帧率有两种策略：

| 模式 | 做法 | 实测偏差（14 段） |
|---|---|---|
| 转恒定帧率（默认） | 切点吸附帧网格，`-fps_mode cfr -r 源帧率` | **+41 ms** |
| 保留源时间戳 | 不吸附、不传 `-r`，`-fps_mode vfr` | +333 ms（8 帧） |

CFR 偏差小，是因为把切点对齐到了帧网格；preserve 保住了每段原始时间戳，但片段边界只能落在实际帧上，误差会累积。CFR 素材用默认模式，真正的 VFR 素材才需要 preserve。

导出带 `-map_metadata -1 -map_chapters -1`：源片的章节在 MP4 里会变成一条 `bin_data` 数据轨，还带着原标题和章节名，与剪辑内容无关，因此全部丢弃。实测源有 6 章节 + 1 条数据轨，成片只剩 video + audio 两条流、零章节。

输出路径会做两项保护：与源视频相同则直接拒绝（否则 `os.replace` 会覆盖原片），已存在则命令行覆盖、界面先弹确认。

## 已知限制

- **仅支持日语**。转写阶段固定 `language="ja"`。
- **短句和强 BGM 段的声纹分不稳定**。这类句子会落在阈值下方，需要手动补勾。
- **同一声优配多个角色时无法区分**。声纹只能识别"这是谁的声音"，不能识别"这是在演哪个角色"。
- **模型只显示本地已安装的**。当前只有 large-v3，换模型需要先手动放置权重。
- **试听是音频加一张起始帧**，不是完整播放器。核对一句话零点几秒就能听到，但看不到连续动作；需要看完整画面还是得用外部播放器。
- **换音轨必须重新分析**。导出校验会比较所选音轨与活动 run 的音轨，不一致直接拒绝；界面同时禁用「生成成片」，不会出现"新音轨配旧切点"。
- **指纹缓存依赖路径、大小和修改时间**。极少数原地改写同尺寸文件并恢复 `mtime` 的工具可能让缓存返回旧摘要。用 `migrate_jobs.py --rehash` 或删掉 `work/.cache/fingerprints.json` 即可重算。
- **VFR 素材默认转 CFR**。想保原节奏就选「保留源时间戳」，代价是时长偏差变大（实测 41 ms → 333 ms）。
- **VFR 判定是启发式**。现在会抽样 120 帧比较间隔分布，恒速片不会被时基舍入误判；但极短的片子（不足 10 个间隔）只能给出「无法确认」，此时可以自己试一次 preserve 对比。
- **队列串行执行**，不并发。显存和 CPU 只有一份，并发转写只会互相拖慢；要多机并行可以复制项目目录，或用 `CLIP_JOBS_DIR` 指向不同的任务目录。
- **队列里的条目不能改参数**。加入后只能移除重加；这样"跑的是不是我当时看到的参数"没有歧义。
- **标注集只有一集**。`labels.json` 与内置的 32 句都来自同一集，跨作品的阈值稳定性还没验证过。
